QUESTION 01

What is EPP's request pipeline: filter, score, and pick?

Short answer: EPP is a decision service. The proxy holds the client's connection, pauses each request, and asks EPP: "which model pod should get this?" EPP resolves the request, gathers data, optionally queues it, then runs filter → score → pick over the candidate pods and hands one destination back. It never carries the inference bytes itself.

🏥
Analogy: hospital triage Think of EPP as the triage desk in an emergency room. Patients (requests) never get treated at the desk. The desk checks who's eligible (filter: "Dr. B is off-shift"), ranks the options (score: "Dr. A already has this patient's chart and a short line"), and assigns one doctor (pick). The actual treatment — prefill, decode, KV cache — happens in the treatment room (the vLLM pod). If the desk burns down, doctors keep treating current patients; only the routing intelligence is lost.

1 Two planes: configuration vs. the live request

The single biggest source of confusion: InferencePool is not on the request path. It's Kubernetes configuration that sets the stage. Once the stage is set, live requests flow only through proxy → EPP → pod.

Configuration plane (sets up) vs. request plane (runs per request)
Kubernetes config Client Proxy EPP Model server
ⓘ Who owns what
The proxy owns connections. EPP owns the routing decision. The model server owns prefill, decode, and the KV-cache tensors. InferencePool owns nothing at runtime — it's declarative configuration that tells the controller and EPP how to set themselves up.

2 Inside EPP: the full Director pipeline

"Filter, score, pick" is the famous part, but it's only the core of a longer pipeline called the Director. Here's the real per-request sequence, in order.

Director.HandleRequest — one request's journey through EPP
Filter (eliminate) Score (rank) Pick (choose) Director stages
  1. Filters are vetoes, not opinions. Filter order can matter for performance, but semantically the result is the intersection: only pods passing every filter survive.
  2. Scorers never eliminate. A pod with a terrible score is still pickable (and weighted-random might even pick it). Elimination is exclusively the filter's job.
  3. The picker is pluggable. Max-score is the default; weighted-random trades some optimality for load spreading; a custom picker can implement anything.

3 What breaks when EPP breaks?

EPP does hold state — discovered endpoints, metric snapshots, prefix-location metadata, flow-control queues, in-flight request context. But none of it is model state. Weights, conversations, and KV tensors all live in the model servers. Most EPP state can be rebuilt after a restart, though a cold replica may briefly make worse locality decisions (Q4 covers this).

The real question is: what does the proxy do when EPP doesn't answer? That's governed by failureMode on the extension config:

ModeWhen EPP fails…Trade-off
FailClose (GIE default) The proxy drops the request. No "dumb" routing ever happens — but EPP becomes a hard availability dependency.
FailOpen (llm-d chart default) The proxy picks an endpoint itself, with its ordinary load balancing. Requests keep flowing — but prefix locality, flow control, QoS, and the picker are all bypassed. No promise of round-robin or stream continuity.
⚠ Common misconception
"Fail-open means graceful degradation to round-robin." Not guaranteed. Fail-open only means the parent data plane chooses however it normally would. Which algorithm that is depends entirely on the proxy's own configuration — and in-flight streams get no special protection.

For high availability, EPP replicas can run with a warm-standby pattern: the ext-proc server runs on every replica (no leader election for serving), while a separate feature can pre-populate a non-leader's datastores so it isn't cold when it takes over. How availability actually composes — active serving, leader-controlled discovery, warm standby, proxy fail-open — is a deployment decision, not a single built-in behavior.

Key takeaways

  • EPP decides, the proxy moves bytes, the model server computes. Three roles, never mixed.
  • InferencePool is configuration, not a runtime hop — and it's optional if a discovery plugin supplies endpoints.
  • The pipeline is bigger than three steps: resolve → produce data → flow control → filter → score → pick → prepare destination.
  • Filters veto (irreversibly), scorers rank (weighted 2/2/3 by default), the picker chooses one (max-score by default).
  • EPP failure behavior lives in the proxy: FailClose drops, FailOpen bypasses all EPP intelligence. llm-d's chart ships FailOpen.
