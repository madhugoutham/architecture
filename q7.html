QUESTION 07

Is metrics collection and scoring agnostic to vLLM and SGLang?

Short answer: Engine-adaptable, not engine-independent. EPP polls a common Prometheus-format /metrics path, then maps engine-specific names into shared fields that scorers understand. That works for vLLM and SGLang metrics — but precise prefix is a separate boundary: an SGLang event adapter exists, yet the current precise producer hardwires the vLLM adapter.

🔌
Analogy: travel adapters Your laptop (the common scorers) runs the same software everywhere. Wall plugs differ by country (vLLM vs. SGLang metric names), so you use a travel adapter ((mapping registry). That does not mean every country's socket delivers the same wattage — units and freshness can differ. And the fancy "smart home" remote that talks a proprietary protocol (precise KV events) might still only ship with the US plug soldered on — even if a UK adapter board exists in the parts bin.

1 Metrics path: label → map → common fields → scorers

The endpoint label llm-d.ai/engine-type selects which metric name map to use. If the label is missing, EPP falls back to the configured default mapping — convenient, but dangerous if the pod isn't actually that engine.

An unlabeled or mislabeled endpoint can be interpreted with the default engine map. That is operationally convenient and can silently produce missing or wrong fields. Treat engine support as a capability matrix, not one Boolean.

Key takeaways

  • Adaptable, not independent — common scorers sit behind engine-specific maps.
  • llm-d.ai/engine-type selects the map; missing labels fall back to the default (risky).
  • Normalization proves syntax was parsed — not that units and semantics match.
  • Precise prefix is a second boundary — SGLang adapter exists; producer still hardwires vLLM.
  • Exact-token / render path shown at this revision is vLLM HTTP render.
