QUESTION 07

Is metrics collection and scoring agnostic to vLLM and SGLang?

Short answer: The metrics subsystem is engine-adaptable, not engine-independent. EPP polls a common Prometheus-format endpoint, then uses the llm-d.ai/engine-type label to pick a mapping into common fields that scorers consume. That supports vLLM and SGLang metrics — but normalization ≠ semantic parity. Precise-prefix has a separate boundary: an SGLang KV-event adapter exists, yet the current precise producer hardwires the vLLM adapter.

🔌
Analogy: universal power adapters The same laptop can run from different wall plugs once you attach the right adapter — US, EU, UK. The charger still expects a familiar voltage on the laptop side. That is metrics normalization. But not every country's socket delivers the same wattage or frequency — adapter success ≠ identical power quality. And the fancy surge-protector lane for "precise" events may only ship with a US plug soldered in, even if an EU adapter sits in the parts bin unused.

1 Adapter architecture: label → map → common fields

One HTTP metrics source polls every endpoint. The endpoint's llm-d.ai/engine-type label selects which name mapping to apply. Unlabeled endpoints silently fall back to the configured default mapping — convenient, but dangerous if the engine is not actually the default (wrong or missing fields).

Built-in mappings include vLLM, SGLang, TensorRT-LLM Serve, and Triton variants. vLLM maps vllm:num_requests_waiting, vllm:num_requests_running, vllm:kv_cache_usage_perc. SGLang maps sglang:num_queue_reqs, sglang:num_running_reqs, sglang:token_usage.

⚠ Silent default mapping
An unlabeled or mislabeled endpoint can be interpreted with the default engine mapping. That is operationally convenient — and can silently produce missing or wrong fields if the engine is not actually the default.
⚠ Normalization ≠ semantic parity
Engines may omit LoRA data, represent utilization on a different scale, or update gauges on a different cadence. A successful scrape only proves text was fetched and parsed. A valid adapter must define syntax and semantics: name, labels, unit/range, aggregation, absence behavior, freshness.

2 Capability matrix — treat support as rows, not a Boolean

Token production is another engine boundary. The exact-token path in the current router calls vLLM render endpoints. No equivalent SGLang render path is proven at the pinned revision. An engine-neutral precise path would need aligned tokenization, chat-template rendering, model identity, block size, hash construction, event schema, and adapter selection — metrics-name compatibility addresses none of those.

  2. Compare under the same workload — raw metrics, normalized fields, scorer outputs, chosen endpoints, prefix hashes, and event-driven index changes.
  3. Define absence policy — unsupported or missing signals need an explicit operating rule, not a quiet vLLM fallback.
ⓘ Before declaring parity
Run the same controlled workload on each engine. Metrics-name compatibility alone is never enough to claim end-to-end precise-prefix or exact-token parity.

Key takeaways

  • Metrics are engine-adaptable, not engine-independent — label → mapping → common fields → scorers.
  • Unlabeled endpoints fall back to the default mapping; mislabels can silently corrupt fields.
  • Built-in maps cover vLLM and SGLang (plus TensorRT-LLM Serve / Triton variants).
  • Normalization ≠ semantic parity — units, scales, cadence, and missing signals can still differ.
  • Precise-prefix is a separate boundary: SGLang adapter code exists, but the producer hardwires NewVLLMAdapter().
  • Exact render/token path shown at this revision is vLLM-only; treat support as a capability matrix.
