QUESTION 02

Which vLLM metrics are collected, and which affect the default score?

Short answer: EPP collects more than it scores. Background collectors poll every model pod's /metrics endpoint (every 50 ms by default) and an extractor normalizes engine-specific names into common fields. But the shipped default score uses only three signals — queue depth (weight 2), KV-cache utilization (weight 2), and prefix locality (weight 3) — and prefix locality doesn't come from /metrics at all.

✈️
Analogy: a pilot's dashboard vs. the three gauges used for landing A cockpit displays dozens of instruments — everything the aircraft can measure gets collected and shown. But on final approach, the pilot actually flies with three: airspeed, altitude, and glideslope. That's the default score. And notice: the glideslope doesn't come from the aircraft's own sensors at all — it's beamed up from equipment on the ground (that's prefix locality, which comes from EPP's prefix index, not from any pod's /metrics). Meanwhile the flight data recorder (Prometheus) logs every instrument for post-flight analysis — but it never flies the plane.

1 How metrics reach EPP: background, not per request

The first thing to internalize: EPP never phones a pod for metrics while a request is waiting. When EPP discovers an endpoint, it starts one background collector for it. Each collector runs on its own timer (default 50 ms), fetches the pod's /metrics page over plain HTTP, and hands the parsed samples to an extractor that translates engine-specific names into EPP's common endpoint fields. The result is published as an in-memory snapshot — one per pod, always the latest completed read.

When a real inference request arrives, the scheduler simply reads those snapshots. There is no request-time HTTP fan-out to the fleet.

ⓘ The 50 ms arithmetic
Every EPP replica runs its own collectors. At the default 50 ms interval, 100 endpoints mean roughly 2,000 background GETs per second per EPP replica — before errors or retries. That number describes collection load, not request latency, and it isn't a fleet-size ceiling; the interval is configurable.
⚠ Stale snapshots are your problem, not EPP's
On a timeout, parse error, or endpoint restart, the collector records the error and keeps the last published snapshot. There is no universal "too old → exclude this pod" rule: the active plugin's missing-data behavior decides what happens. If freshness matters to your deployment, you need a deliberate refresh interval, an explicit stale-data policy, and monitoring of poll failures.

2 Collected ≠ scored: the funnel

Here's the distinction this whole question hinges on. EPP may collect a field because a producer, filter, or optional scorer could need it — that does not add the field to the shipped default weighted score. And a metric exported for Prometheus monitoring doesn't automatically enter EPP's decision path either. Only the plugin configuration decides what changes a routing decision.

ⓘ Three signals, three different questions
Queue depth asks how much work is queued. KV utilization asks how full the cache is. Prefix locality asks where a matching prefix is believed to exist. They're combined precisely because no single one answers all three — and locality deliberately dominates (weight 3), since skipping redundant prefill is the biggest latency win.

Key takeaways

  • Collection ≠ scoring. A field being extracted — or exported to Prometheus — never means it changes a routing decision. Plugin configuration decides that.
  • The default score is 2·queue + 2·KV-utilization + 3·prefix-locality — and prefix locality comes from the prefix index, not from any pod's /metrics.
  • Collectors poll each endpoint every 50 ms (default) in the background; the request path only reads in-memory snapshots. No request-time HTTP fan-out.
  • Running requests, LoRA info, and cache configuration are collected but are not default score terms — they serve configured filters and producers.
  • Prometheus is a separate, independent consumer for dashboards and alerts. It is never in the scoring path.
  • Failed polls keep the last snapshot published. There's no universal staleness rejection — and metric names can drift across revisions and distributions.
