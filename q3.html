QUESTION 03

Does EPP run a tokenizer?

Short answer: not the model's tokenizer, no — at least not universally. EPP has a pluggable token producer with three backends: a cheap local estimate mode (the default fallback), a request-time HTTP call to a vLLM render service, and a deprecated Unix-socket sidecar path. These produce identifiers for routing. The tokenization that actually feeds the model always happens at the model server.

📮
Analogy: a mailroom sorting by zip code without reading letters A mailroom doesn't read your letter to route it — it looks at the zip code on the envelope and drops it in the right bin. EPP's estimate mode is like that: it chops the raw bytes of your prompt into fixed-size chunks and turns them into stable IDs. Two identical envelopes always land in the same bin, which is all routing needs. But the zip code is not the letter's contents — just as pseudo-tokens are not the model's tokens. Only the recipient (the model server) actually opens and reads the letter, with its real tokenizer.

1 Three ways EPP gets token IDs for routing

During request data production (stage 2 of the Director pipeline from Q1), EPP needs token-like identifiers from the prompt so it can compute prefix block keys — the lookup keys for "which pod probably has this prefix cached?". The configured token producer supplies them, and it has three backend paths. When neither explicit backend is configured, the factory falls back to estimate mode.

✕ No silent rescue on render failure
The backend-selection code does not implement an automatic fallback from a failed HTTP render call to estimate mode. A slow, unavailable, or incompatible render service affects that request's EPP processing directly — it's request data production, not a background metrics poll that can quietly go stale.
ⓘ Render ≠ metrics collection
Don't confuse the render call with the metric collectors from Q2. Collectors poll /metrics on a timer in the background; the render call runs inside a request's data-production stage because the prefix plugins need its output for the current scheduling decision. Different loop, different failure blast radius.

2 Routing tokens vs. execution tokens: who owns what

The word "tokenizer" hides two different jobs. Routing tokenization only needs stable identifiers so prefix lookups group identical inputs. Execution tokenization must produce the exact token sequence the model computes over — and that always belongs to the model server, regardless of which token producer EPP runs.

This is also why "precise prefix" is often misread. Precise describes the event-backed lookup — routing keys correlated with KV-cache state reported by engine events — not a secret model tokenizer inside EPP. In fact, the current precise producer rejects its former internal tokenizer configuration and demands token data from an upstream producer.

The render service's latency, timeout, availability, and model/template alignment are all deployment parameters, not code guarantees. A deployment can depend on exact model tokenization through an external or legacy producer — but the default estimate path and the precise plugin do not embed that tokenizer inside EPP.

Key takeaways

  • EPP does not universally embed the model's tokenizer. It runs a token producer whose default fallback packs input bytes 4-at-a-time into deterministic pseudo-token IDs.
  • Estimate tokens are stable, cheap — and not the model's tokens. An estimate-derived key isn't guaranteed to match a key from vLLM's tokenizer.
  • The vLLM render backend gets model-compatible token data via a request-time HTTP call — adding a network dependency on the hot path, with no automatic fallback to estimate on failure.
  • The model server always owns execution tokenization. Routing tokens are metadata; execution tokens are what actually gets computed.
  • "Precise" means event-backed lookup, not a hidden tokenizer. The precise producer requires token data from an upstream producer.
  • Compatibility is a contract: token IDs, model identity, block size, hash inputs, and event metadata must align — or KV reuse is silently missed.
