QUESTION 04

What prefix-to-pod state does EPP keep, and what happens on restart?

Short answer: EPP is stateful for routing metadata, stateless for the model's data plane. It keeps mappings that answer one question — "which pod probably has the longest reusable prefix?" — populated either from its own routing history (approximate) or from engine KV events (precise). On restart, those in-memory maps vanish; the GPU KV tensors on the model servers do not. Inference stays correct — only the routing intelligence goes cold and rebuilds slowly.

🍽️
Analogy: the maître d's memory vs. the kitchen's actual food A maître d' remembers regulars: "Table 7's waiter already knows this party's order." That memory makes service faster — but it isn't the food. The approximate maître d' remembers only where he seated people (he can be wrong if a party left, or was seated by a colleague he never saw). The precise maître d' gets notes from the kitchen every time a dish is prepped or thrown out — better, but only as good as the notes that actually arrive. If the maître d' is replaced overnight, the kitchen and all its prepped food remain; the new hire just seats people less cleverly until his memory rebuilds.

1 Two ways to remember: approximate vs. precise

Both modes feed the same consumer — the prefix scorer that weighs locality in the default score (weight 3, from Q2). What differs is the evidence. Approximate mode records EPP's own routing decisions. Precise mode builds an index from KV-cache lifecycle events emitted by the engines. Each has a distinct shape, a distinct failure mode, and a distinct restart story.

ⓘ Evidence, not truth
Approximate mode answers "where did I route this prefix before?" Precise mode answers "where do the events I received say compatible blocks live?" Both are predictions. Precise needs stronger compatibility (Q3's contract) and is still bounded by event loss, late joins, engine eviction, and changes after the scheduling decision. Neither is a reservation.

2 The restart story: what dies, what survives, what rebuilds

Here's the moment that makes the stateful/stateless distinction concrete. Kill an EPP pod and watch what happens to each kind of state. The punchline: inference correctness is never tied to EPP metadata survival — but routing quality dips until the memory rebuilds.

Timeline of an EPP restart — warm → gone → rebuilding → reconverged

⚠ Replicas can disagree
Every EPP replica builds its own view. Approximate replicas see different routing histories; precise replicas can join at different times or miss different events. A warm non-leader datastore or an external index can reduce cold-start cost, but neither by itself proves identical state across replicas. After a restart or disconnect, recovery can come from future events, preserved storage, or speculative history — a true snapshot/replay mechanism helps only when it's actually present and verified.
  1. Approximate is a bet on your own past. Fast and local, but blind to evictions, failures after selection, and anything other replicas did.
  2. Precise is a bet on the event stream. More accurate while events flow, but only as complete as what one replica actually received over ZMQ.
  3. Restart resets the bet, not the cache. The engine's KV tensors are untouched; only EPP's knowledge of them must be re-earned.

Key takeaways

  • EPP is stateful for routing metadata, stateless for the model data plane. No weights, no KV bytes, no authoritative conversation state.
  • Approximate mode = process-local hashToPods + per-pod bounded LRU, updated after selection — it records decisions, not engine confirmations, and can be optimistic or miss other replicas' residency.
  • Precise mode = indexer + tier-aware scorer + KV-event pool + subscribers; default backend is in-memory, Redis optional. Events: BlockStored, BlockRemoved, AllBlocksCleared (pod-wide, all tiers).
  • The event pool shards by pod, so same-pod order is preserved — but ZMQ has no durable log, gap detection, or replay in the inspected path.
  • On restart: in-memory maps vanish, GPU KV tensors survive, inference stays correct — locality knowledge rebuilds slowly from new routes and events.
  • Redis persists entries but can persist stale ones (durable index + lossy stream), and replicas can legitimately disagree.
