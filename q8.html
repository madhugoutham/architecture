QUESTION 08

What happens when KV-cache blocks are evicted, and how does EPP learn about it?

Short answer: it depends entirely on the mode. In approximate mode, EPP never learns about an individual engine eviction — its index records where requests were routed, not what the engine still holds. In precise mode, EPP consumes explicit BlockRemoved and AllBlocksCleared events over ZMQ — but those events are optional, asynchronous, and lossy, and the EPP subscriber does not detect gaps or request replays. "Precise" names the correlation mechanism, not a consistency guarantee.

📮
Analogy: the card catalog and the postcards Picture a library card catalog that only updates when the librarian mails you a postcard about books that were moved or discarded. If every postcard arrives, your catalog matches the shelves. But the mail is best-effort: the librarian's outbox has a size limit and quietly drops postcards when you're slow to read them — and you never count the stamps to notice one is missing. Miss a postcard, and your catalog confidently lies. That is EPP's precise mode. Approximate mode is worse in a different way: it's a diary of where you sent people, and the library never mails you anything at all.

1 Two modes, two completely different answers

First, the vocabulary. The KV cache is the set of per-token attention tensors a model server keeps on the GPU so it can skip re-computing a prompt prefix. Eviction is the engine discarding cached blocks to free memory — a routine, engine-internal event. The question is whether EPP, sitting outside the engine, ever hears about it.

Approximate mode keeps a process-local map of "prefix → pods I routed it to," with a bounded LRU (least-recently-used list) per pod. It records a routing decision, not a confirmation from the engine. The engine can evict a block one second later and the routing history will still predict a hit. Entries only age out through EPP's own LRU pressure or when an inactive pod is cleaned up — neither of those is an engine notification.

Precise mode subscribes to an explicit event stream from the engine: BlockStored, BlockRemoved, and AllBlocksCleared. When a remove event arrives and is applied, the matching index entry is deleted. That is genuinely more accurate — as long as every event is produced, transported, and applied. The rest of this page is about where that chain can break.

2 The precise event pipeline, end to end

Events travel from the engine to the index through several hand-offs. Each hand-off has its own failure boundary. ZMQ here is a lightweight pub/sub messaging library — fast, brokerless, and with no delivery guarantee once its buffers fill.

⚠ Events are off by default
vLLM's KV-event configuration is disabled by default. A cluster that never enabled it runs precise mode against an event stream that doesn't exist. Everything on this page about remove events assumes an operator explicitly turned event publishing on.
ⓘ There is no MOVED event
The EPP event schema is exactly three types: BlockStored, BlockRemoved, AllBlocksCleared. A block moving between tiers (say GPU → CPU) is represented only by whatever store/remove information the engine or connector actually emits — not by a dedicated move event.

3 When a postcard goes missing: the stale-positive scenario

Here's the concrete failure everyone should be able to narrate: a BlockRemoved event is dropped, and EPP routes the next request toward a cache hit that no longer exists.

One dropped BlockRemoved → one phantom cache hit

The full consistency model follows directly from "a derived view of received events":

StateCauseEffect on routing
Stale positive A BlockRemoved was missed EPP predicts hits that miss → wasted locality routing, recompute at the engine
Stale negative A BlockStored was missed EPP overlooks real residency → misses a locality win it could have had
Empty EPP restart with the in-memory backend All locality knowledge gone until new events rebuild it
Replica divergence Replicas subscribed at different times or missed different events Two EPP replicas can score the same request differently
⚠ Redis does not fix this
An optional Redis index backend persists entries across an EPP restart — but persistence cannot repair an event that was never received. A durable index fed by a lossy stream simply preserves possibly-stale data more reliably. Correct recovery would need a proven snapshot, replay, or reconciliation contract, which the inspected path does not implement.
ⓘ What to monitor until a gap/replay contract exists
Watch the event receive rate, adapter errors, work-queue depth, index size, and sequence discontinuity (externally — EPP won't flag it for you). The safe way to describe what precise mode gives you: "event-correlated prefix metadata with defined loss boundaries" — not "instant true cache state."

Key takeaways

  • Approximate mode never learns about eviction. It records routing decisions; entries fade only through EPP's own LRU pressure or inactive-pod cleanup.
  • Precise mode consumes BlockStored / BlockRemoved / AllBlocksCleared — and vLLM event publishing is disabled by default.
  • The transport is lossy by design: ZMQ's high-water mark can drop events, and EPP's subscriber does no gap detection and no replay requests — vLLM's replay endpoint is not an EPP recovery mechanism.
  • AllBlocksCleared wipes every tier for the pod; tier-scoped clears are unsupported at this revision.
  • The consistency model has four faces: stale positive, stale negative, empty after restart, replica divergence. Redis persistence changes none of them — it can preserve stale entries, not replay missed events.
  • Say "event-correlated prefix metadata with defined loss boundaries," never "EPP knows the true cache state."
