QUESTION 06

Does EPP scrape metrics for every request, and how does collection scale to ~100 model servers?

Short answer: No — EPP does not scrape per request. Each discovered endpoint gets a background collector on a periodic ticker (50 ms default when no positive interval is configured). Collectors GET /metrics, parse Prometheus text, and publish snapshots via atomic pointer swap. The request path only reads those snapshots. At 100 endpoints × 50 ms × 1 replica ≈ 2,000 GETs/sec — a capacity estimate, not a latency claim or fleet ceiling.

🩺
Analogy: nurse on rounds, not a blood test on demand A nurse checks patient monitors on rounds every few minutes and writes the latest vitals on a clipboard. When the doctor asks "who looks busiest?", they read the clipboard — they do not run a new blood panel for every question. EPP's collectors are the nurse; the request path is the doctor. Prometheus/Grafana is a separate charting service that may also glance at the monitors, but removing it does not stop the nurse.

1 Four planes: discovery, background, request, observability

Confusing these planes is the main scaling mistake. Discovery learns which endpoints exist. Background collectors keep snapshots fresh. The request path only reads memory. Prometheus is an entirely separate consumer for dashboards — not required for routing.

3 Transport, failure, and what to measure

The shared HTTP transport keeps a large idle-connection pool and up to 2 idle connections per host. The client has a 10-second upper guard; the collector supplies its own bounded context, so the effective deadline is whichever limit fires first — not an unconditional 10-second scrape.

On timeout or non-200, the collector records an error and retains the last snapshot. Ordinary queue and KV scorers read published fields without using UpdateTime as a universal rejection gate. Staleness policy is the deployment's job — the server's metrics-staleness setting is not, by itself, a universal scheduler freshness check.

⚠ Stale data can still win
Repeated collection failures can leave old values eligible for scheduling unless another configured plugin or policy handles freshness. Choose interval, stale-data policy, and poll-failure alerts deliberately.
  1. Configured polling interval — confirm the value actually loaded (default vs. override).
  2. Actual GET rate from EPP to model servers — compare to N × (1/T) × R.
  3. Snapshot age and failure rate — how often collectors error; how old published data is.
  4. Scheduler duration vs. candidate count — request-path CPU still grows with N even without HTTP fan-out.
ⓘ Latency claims need a full recipe
A latency number is only defensible with replica count, endpoint count, interval, plugin profile, transport security, response size, hardware, and percentile. The code proves the mechanism and default — not a universal ceiling.

Key takeaways

  • No per-request scrape — background collectors publish snapshots; the request path only reads them.
  • One collector per endpoint on a ticker; 50 ms is the default only when no positive interval is set.
  • Publish path: GET → parse → clone/update → atomic pointer swap.
  • Rate ≈ N × (1/T) × R — 100 @ 50 ms @ 1 replica ≈ 2,000 GETs/sec; capacity estimate, not a fleet ceiling.
  • On failure, last snapshot is retained; scorers do not universally reject stale data.
  • Prometheus is a separate path — removing it does not stop EPP's direct routing scrapes.
