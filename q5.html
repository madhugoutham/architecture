QUESTION 05

How does prefix matching participate in prefill/decode disaggregation?

Short answer: Decode is scheduled first. Prefix evidence helps pick that decode endpoint, then a P/D decider looks at how much of the prompt that endpoint already has cached. If the non-cached remainder is small enough, decode does prefill locally; otherwise EPP optionally runs encode and a separate prefill profile to pick a prefill worker. EPP never moves KV tensors — it only returns endpoints and metadata.

🍽️
Analogy: prep kitchen vs. main stove Think of a restaurant that decides whether to prep ingredients at a prep kitchen or at the main stove. First you assign the cook who will finish and plate the dish (decode). Then you check how much of the mise en place is already chopped at that cook's station. If most of it is ready, they finish locally. If almost nothing is prepped, you send the heavy chopping to the prep kitchen and ferry the results over — EPP picks the stations; it does not carry the food itself.

1 Decode first, then decide whether to split

Prefill processes the whole prompt up front — it is compute-bound. Decode generates tokens one-by-one — it is latency-bound. Disaggregation means running those two phases on different pods so each can be sized and scheduled for its workload.

The counter-intuitive fact: in the unified disaggregation handler, the decode profile runs first. The first concrete placement decision is the decode endpoint D, not the prefill endpoint. Prefix producers and scorers may influence that decode pick alongside queue and utilization signals.

ⓘ Two different placement questions
Decode selection assigns ownership of the generation loop. The P/D decision then asks whether separate prompt computation is warranted given what that selected decode endpoint is believed to cache. A long prompt does not force disaggregation if most of its prefix already lives at D.

2 The threshold: cached prefix vs. non-cached remainder

The decider uses raw cached-block counts, not tier weights. Tier-aware scoring (valuing GPU copies differently from CPU) is a separate mechanism used when ranking endpoints. The split decision estimates non-cached tokens from the unweighted block count and compares that to a configured threshold.

⚠ Unweighted blocks ≠ tier-aware score
A scheduling scorer can weight GPU copies above CPU when ranking endpoints. The P/D threshold path at this revision still uses the raw cached-block count to estimate non-cached tokens. Tier-aware preference does not make the split decision itself tier-cost aware.

3 What EPP does not guarantee after the decision

EPP's prefix state is metadata throughout. It can report cached block counts or weighted locality for scheduling, but it does not own or transfer tensor bytes. The prefill worker computes missing KV; the connector moves or exposes it. NIXL is one possible connector technology — coordinator, sidecar, peer-to-peer, and shared-storage deployments can differ in headers, ports, call direction, readiness, and retry ownership.

Conditional decode is a separate optional path from the unified handler. With Prefer: if-available, the Director can accept a decode endpoint that has a cache match or return HTTP 412 so a coordinator can restart the full pipeline. That handshake does not change the decode-first ordering inside the unified disaggregation profile.

  1. Valid decision, failed execution. Prefill, KV transfer, or decode admission can still fail after EPP returns a correct pair.
  2. Stale prefix metadata. Approximate history may overstate residency after eviction; precise state may miss events — either can pick the wrong local/disagg path.
  3. Score is not a reservation. A high prefix score does not prove the block will still be present when execution starts.
  4. Retries are deployment-specific. Retrying the original request can repeat prefill; retrying only a transfer needs identity/idempotency the scheduler alone cannot supply.
⚠ Fail-open bypasses the whole pair
If the proxy is FailOpen and EPP does not answer, the parent data plane picks an endpoint itself — bypassing the chosen P/D pair and locality policy entirely.

Key takeaways

  • Decode is scheduled first — the first concrete placement is D, then the P/D decider runs.
  • The decider uses D's unweighted cached-block count and a non-cached-token threshold — not tier weights.
  • Local path: D does prefill + decode. Disagg path: optional encode + prefill profile → P, then connector → D.
  • EPP never moves KV tensors — it selects endpoints and returns metadata; connectors (NIXL optional) handle transfer.
  • Conditional decode (Prefer: if-available → possible 412) is a separate optional gate.
  • A right decision can still fail at prefill, transfer, or decode admission; stale prefix metadata misleads the split.
