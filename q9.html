QUESTION 09

How do CPU offloading and LMCache affect EPP prefix scoring?

Short answer: in precise mode EPP can represent CPU-resident KV blocks and score them lower than GPU-resident ones — the shipped tier weights are gpu 1.0, cpu 0.8. EPP never inspects CPU memory or calls LMCache at routing time; it relies on tier-bearing events. Native vLLM CPU offloading emits both stores and evictions, so EPP can track both. The LMCache wrapper at the pinned revision converts every event into a store — evictions never propagate through that path, so EPP can keep stale positives.

🚗
Analogy: valet parking with a garage across the street Think of the GPU as the front lot right by the restaurant door and the CPU as a garage across the street. The valet desk (EPP) keeps a ticket book of where each car is. A car in the garage is still retrievable — just slower — so the desk values a garage ticket a bit less than a front-lot ticket (0.8 vs 1.0). Now two twists: if a ticket names a lot the desk has never heard of, the desk assumes it's the front lot (full value!). And one of the garage operators (LMCache) mails in new tickets but never reports towing a car away — so the desk keeps promising cars that are long gone.

1 Tier weights: how a CPU block scores against a GPU block

A tier is the physical location of a KV block: GPU memory, CPU memory, a filesystem, an object store. In precise mode, every index entry carries a tier alongside the pod, and the scorer applies a configured weight per tier. The defaults — gpu: 1.0, cpu: 0.8 — are routing preferences, not measured latencies. They just say: for an otherwise comparable prefix, a GPU-resident block should count for more than a CPU-resident one.

The algorithm walks the request's prefix block by block. For each block, each pod contributes its highest configured tier weight for that block — a pod holding the same block on both GPU and CPU takes the larger weight once, with no double counting. Weights accumulate only while the prefix stays consecutive; the streak stops at the first block a pod doesn't have. The weight map lives under the precise producer's parameters.indexerConfig.kvCacheBackendConfigs.

⚠ The unconfigured-tier fallback
fillMaxWeights starts at 1.0 and replaces it only when the tier name exists in the configured weight map. Any connector-specific or misspelled tier name — fs, obj, anything unexpected — is therefore valued like GPU. The shipped defaults define only gpu and cpu. Operators must verify that event tier strings normalize to configured keys and deliberately configure every tier they admit.
ⓘ The int-quantization quirk
The scorer accumulates floating-point weights, but the producer converts each aggregate to int before storing the published match info. With the default CPU weight 0.8: one CPU-only matched block → 0; two → 1. Keep this in mind when interpreting per-tier cached-block counts on an endpoint.

2 How a CPU location reaches EPP — and where LMCache differs

CPU offloading means the engine moves KV blocks from GPU memory to CPU memory to free GPU space, keeping them retrievable without a full recompute. LMCache is an external KV-cache engine that vLLM can plug in through a connector. Both can tell EPP about CPU residency — but through very different event paths, with very different completeness.

A detail worth knowing first: an offload event can be location-only — block hashes plus a new tier, without repeating the tokens. EPP resolves those engine keys through its existing engine-key → request-key mapping. If a key is unknown (the original store event was missed, or the index restarted), the update is skipped, not guessed.

⚠ Keep the LMCache claim narrow
The finding is specific: this wrapper method, at this pinned vLLM revision, converts every returned event into BlockStored with no BlockRemoved conversion. It is not a statement about every LMCache version or every external integration. A deployment claiming eviction-correct LMCache routing must identify the exact LMCache version, the event object schema, the wrapper conversion, and an end-to-end remove test.
ⓘ Skipped, not guessed
When a location-only offload event references engine keys EPP has never seen — because the original store event was missed or the index restarted — EPP skips the update rather than inventing an entry. That's the safe choice, but it means one missed store can silently suppress all later tier updates for those blocks.

3 Setting tier weights like an operator, not a copy-paster

The 1.0 / 0.8 defaults are reasonable starting preferences for GPU and CPU, but the right values for your deployment come from measurement: what does using a hit on that tier actually cost relative to recomputing, under your current load?

  1. Measure before weighting. Capture transfer time, deserialize/copy time, contention, hit probability, and the effect on time to first token for each tier. Derive weights from those costs — don't copy illustrative numbers into production.
  2. Verify tier-name normalization. Confirm that the tier string in real events normalizes to a key in parameters.indexerConfig.kvCacheBackendConfigs. Any unmatched name silently gets the 1.0 fallback.
  3. Test the removal path end to end. Force a CPU eviction and check that EPP's per-tier cached-block counts actually change. If they don't, your eviction events aren't arriving — and every CPU entry is a future stale positive.
  4. Confirm both event kinds arrive. Stores prove the happy path; removals prove the correction path. A connector that only ever sends stores (like the LMCache wrapper above) needs an explicit operating policy.

Key takeaways

  • EPP can score CPU-resident blocks in precise mode — default tier weights are gpu 1.0, cpu 0.8, and they are routing preferences, not measured latencies.
  • The scorer takes each pod's highest tier weight per block, accumulated while the prefix stays consecutive; GPU + CPU copies of the same block are never double-counted.
  • Unknown tier names fall back to weight 1.0 — an unconfigured tier is valued like GPU. Normalize tier strings and configure every admitted tier.
  • Floats accumulate, ints publish: one CPU-only matched block (0.8) publishes as 0; two (1.6) publish as 1.
  • Native CPU offloading emits both stores and evictions via the generic tracker — EPP can learn both, subject to Q8's ZMQ loss boundaries.
  • The LMCache wrapper at the pinned revision converts every event to BlockStored — no removals propagate through that path, so a dropped LMCache entry can leave EPP with a stale positive.
